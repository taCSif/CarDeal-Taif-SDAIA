CarDeal — Demo Report

Saudi Used Car Deal Checker · Know the price. Spot the deal.

What this document is

A step-by-step walkthrough of the running service with screenshots and explanations, so the project can be understood without a live session. Each step states what is shown and what it proves.

Vehicle details → ML model → Estimated price → Deterministic policy → Deal decision (Make&Model, Year, Mileage) (compares with Asking Price) (GOOD / REVIEW / POOR)

The ML model only estimates a price; a separate deterministic policy classifies the deal. Keeping them apart avoids circular reasoning (see DECISIONS.md #1).

1Service running in a container

What is shown: The published container image from GHCR is running (docker ps): container cardeal, mapping host port 8020 to the container's 8000.

What it proves: The service is packaged as a Docker image and runs identically from the published artifact — no local build needed. (The image is built and its Compose stack with PostgreSQL is verified in CI, Step 6.)

2Liveness and readiness are separate

What is shown: /health returns {"status":"ok"} and /ready returns {"status":"ready"}, each with its own trace_id.

What it proves: /health (liveness) and /ready (real readiness) are distinct. /ready only returns 200 after the model is loaded and warmed at startup — never at import time.

3A valid prediction

What is shown: For Toyota Camry / 2021 / 80,000 km / asking 85,000 SAR, the service returns an estimated price of 75,262 SAR, a difference of +9,738 SAR (+12.9%), decision REVIEW, and historical comparables.

What it proves: The ML model produces the estimate; the deterministic policy computes the premium (+12.9%) and, since it falls in (5%, 15%], classifies the deal as REVIEW. Raising only the asking price can never improve the decision (enforced in Step 5).

4A malformed request is rejected

What is shown: Entering an invalid year (1800) and submitting produces a validation error: “Please check the four fields and enter valid values.” — the request is rejected.

What it proves: Input is validated against strict rules (Pydantic extra="forbid" and value ranges). Invalid or out-of-range values are refused with a 422 error that still carries a trace_id.

5A deterministic behavioural test

What is shown: test_directional_behavior: for a fixed vehicle and increasing asking prices [90k … 120k], it asserts the decision severity is non-decreasing (severities == sorted(severities)).

What it proves: The policy is provably directional: as the asking price rises, the decision can only stay the same or get worse (GOOD → REVIEW → POOR), never improve — a real, deterministic behavioural guarantee.

6CI/CD pipeline — all green

What is shown: The GitHub Actions run for the latest commit shows all three jobs passing: quality, docker, and publish.

What it proves: Every push to main is automatically linted, type-checked, architecture-checked, tested (with an 80% coverage gate), trained, image-built, smoke-tested, size-gated (≤500 MB), and published — with no manual steps.

7Image published to GHCR

What is shown: The container package cardeal-taif-sdaia is Public on GitHub Container Registry, tagged by the commit SHA (not :latest).

What it proves: Publishing happens only on main, and every image is traceable to an exact commit — a reproducible, auditable release.

8Honest model metrics

What is shown: metrics.json: 8,035 source rows → 5,385 after cleaning; 4,308 / 1,077 train/test; MAE 21,154 SAR, RMSE 39,622 SAR, R² 0.6916, seed 42.

What it proves: Real, reproducible numbers. The three-feature model has a large error band by design; this limitation (and mileage non-monotonicity) is documented in docs/model_limitations.md, not hidden. The engineering pipeline — not the model's accuracy — is the focus of the project.
